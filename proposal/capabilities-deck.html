Understanding the challenge

The real blockers aren't features

Meridian's inventory dashboard has been functional since 2024. The previous vendor left work unfinished. Three structural problems now block all forward progress:

1. Zero test coverage

Meridian IT cannot safely approve any change — no test suite, no confidence. This single gap has made IT a gatekeeper, not an enabler.

2. Reports module defects

At least eight logged defects. Filters don't apply correctly. Tokyo staff see English-only views. Operations data can't be trusted.

3. No restocking capability

VP Operations Tanaka's team makes purchase decisions manually every week. There is no tool-supported flow for reorder recommendations.

Migration plan — 4 steps

Step 1 — Repository abstraction (Phase 1, Day 1)

Introduce repository pattern in Python. All data access moves through interfaces — JSON files remain behind them. Zero user impact, enables clean swap later.

Step 2 — Schema + data load (Phase 1 close)

CDK provisions Aurora Serverless v2. Migration scripts load JSON into normalised schema. Validation report shared with Meridian before go-live.

Step 3 — Repository swap (Phase 1 → 2)

SQLAlchemy implementations replace JSON implementations. All tests run against PostgreSQL from here. JSON files archived to S3.

Step 4 — Data quality baseline (Phase 2)

Completeness, freshness, and consistency report shared with Tanaka before R2 development. Restocking engine needs trustworthy demand data.

R2 — Restocking Recommendations

Stockout-risk-ranked purchase order suggestions, generated in one click.

days_remaining = stock / avg_daily_demand
risk_score = 1 / days_remaining
order_qty = max(0, reorder_target − stock)
cost = order_qty × unit_cost

Candidates ranked by risk score (high → low). Greedy selection until budget ceiling reached.

Container strategy

Multi-stage Dockerfile; images tagged with Git SHA and pushed to ECR. Rollback = task definition update, no redeployment. ECS rolling deployment with health check gates.
